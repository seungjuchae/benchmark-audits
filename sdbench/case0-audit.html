SDBench

We reviewed the GPT-5 baseline trajectory on Microsoft SDBench’s synthetic case 0. The final diagnosis was correct (Judge 4/5), but we found four problems in how the agent received information. In two, the Gatekeeper returned results that were not requested. In the other two, it generated results that are not in the source case report. All four come from Gatekeeper responses, not from the diagnostic model. See below.

The tests it did name came back “not reported”

Direct immunofluorescence and the bacterial, fungal and AFB stains were on the order, but the Gatekeeper answered them as “not reported.” What was requested and what was returned do not line up.

The Gatekeeper’s own instructions pull in two directions

The prompt forbids diagnosis-identifying information beyond what is requested, and it also tells the Gatekeeper to return an existing report verbatim. It does not define which ancillary tests belong to a biopsy order. This example alone does not establish a definite rule violation.

Gatekeeper prompt · v6_fixed
Prohibited disclosures – never reveal or imply: … any information beyond what is requested that identifies the diagnosis (e.g. "consistent with X" or "suggestive of X")
If the investigation already exists in the vignette → return its report verbatim.

Why this may affect evaluation

If the rule is to return only explicitly named tests, this exceeds scope. If a biopsy order includes the pathology department’s follow-up panel, it may be allowed, but that scope and its full cost must apply to every participant. This is not a claim that the tests are clinically inappropriate.

Why this may affect evaluation

The agent receives a result for a test it did not select. If the benchmark measures test-level information gathering and cost, what is disclosed should match the actual order. If CSF testing is treated as a package, its components and price should be fixed in advance. As with the skin biopsy, whether this is a violation depends on that package boundary.

Benchmark and grading details

How SDBench is scored

For each case, SDBench runs three roles in a loop. The diagnostic agent receives a short case summary that does not reveal the diagnosis and, turn by turn, orders tests, asks questions or commits to a diagnosis. The Gatekeeper answers each order from the case’s full text. When the case contains the result, it returns that; when it does not, its prompt tells it to generate a synthetic result. In this run it sometimes answered “not reported” instead (the first two findings). When the agent commits, a Judge scores the diagnosis against the ground truth on a 1–5 scale; 4–5 counts as correct.

The Gatekeeper and Judge are fixed by the configuration; only the diagnostic agent is being evaluated. So whatever the Gatekeeper discloses feeds straight into the agent’s score.

Reading is_synthetic

is_synthetic is a label the Gatekeeper model sets itself; it is not an independent check. false means the response was not marked as containing fabricated results. It does not certify accuracy, appropriate scope or real-patient provenance. true means generated content is included, not necessarily that the whole response was generated. The source report is itself synthetic.

The label on the right of each finding combines this flag with our own check. Synthetic means the response was flagged true. Source-backed means it was flagged false and we confirmed its findings appear in the source report, apart from the lines answered “not reported.”

What this log supports

This is not evidence that the diagnostic model assumed normal results without ordering tests. The model requested tests; the Gatekeeper supplied extra information or generated missing results. This log alone cannot establish how much that affected the final diagnosis.

The core diagnosis was correct
The model answered IVLBCL after receiving the skin-pathology findings. The log does not support calling this an unsupported guess.
The test-selection process was not validated
Results beyond the explicitly named tests were supplied, and the agent submitted all 36 test requests in one turn.
The Gatekeeper may influence evaluation
The log shows expanded disclosure and generation of missing results. Establishing a causal effect on the final answer requires a separate experiment.
A token-saving motive cannot be established
The agent prompt sets no token objective, and the log records no per-test rationale: the harness never fills the reason field, so it is empty for every entry. We do not infer the model’s intent.

Conditions for a consistent comparison

  1. Define the returned findings and included follow-up panels for each test ID.
  2. Align the test components disclosed to the agent with those included in costing.
  3. Return “unavailable” for missing results, or use reviewed, fixed values shared across participants.
  4. Record source-backed versus generated provenance for each test component, not only for the combined response.
